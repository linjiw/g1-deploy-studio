# Review session · 2026-10-20

Before handing over v0.4 (actuator profiles, predictive anchoring, the L3 launcher, the video), Studio went through an
independent review, three independent verifications of the fixes, and a final regression.
Separate agents did the reviewing and the verifying. The fixes were made here. Each verifier worked on its own data root and
gateway, used the 8790 service read-only, and committed nothing.

**Outcome:** every finding is fixed, or recorded below as by design or open. There were 3 high, 8 medium, 14 low and 12 nits from
the review, and 10 new items (N1–N10) from the verifications. Each fix round was checked by the next verification. The fixes for N9
and N10 (the last round) are checked by new instruments and the final regression, not by a further independent pass.
No critical finding: there is no command path, binding is loopback-only, and POST routes are an allow-list.

## What the review changed

### High: results and run identity

| # | Finding | Fix |
|---|---|---|
| H1 | Torque reaching the source PD clip (139 N·m hip pitch, hip roll and knees; 88 N·m hip yaw; 50 N·m ankles) was not counted, so `g1-current` runs looked unsaturated. Addendum D's "no clamping" claim was wrong | Torque is counted at the effective limit, min(training clip, model clamp), with ≥. `torque_at_limit()` re-derives old runs from their recorded peaks. Addendum D is corrected; Addendum E re-measures: most latency runs drive a leg joint to its limit (9/12 at 160 ms, 34/36 at 200 ms), most often the 50 N·m ankles |
| H2 | Scenario dedupe ignored the actuator profile, so a request could reuse a run made with another profile | The profile is part of the scenario content key |
| H3 | Saved scenarios without a profile re-ran on `g1-current` | A missing field means `source` (the model those runs used). Only new requests default to `g1-current` |

### By design or still open

- **HUD "Speed (fd)":** on recordings without a velocity field, speed is a finite difference, and the label says so.
- **Returning to Rehearse after a run finished elsewhere:** the preset preview is shown over the recording, with a note that the inspector shows the last recording.
- **Never executed: L3 and the L3 launcher.** This session's permission policy blocks starting the real-time chain, so the operator runs it (STATUS open issue 1).
- **Research questions:** latency margin, settling at the goal, the robot's `mode_machine`, ankle limits and the privileged WX block are tracked in [STATUS](STATUS.md#open-issues). They are not Studio defects.

## See it yourself (about 10 minutes)

Open http://127.0.0.1:8790/ (remote: `ssh -N -L 8790:127.0.0.1:8790 <user>@<host>`) once it serves this review's final commit;
the status bar shows the served build. Every run below is an isolated CPU simulation; there is no hardware path.

1. **Replay:** the default recording opens. *Evidence key* in the top bar explains the evidence chips.
   - Scrub the timeline. Open each inspector tab: Intent, Joints, Health, Map, Pipeline, Graph, Source.
   - Labels say what each value is: measured, estimated, commanded or simulator truth. Missing data shows "—" or "Unavailable", never 0.
2. **Arena:** pick a template, drag a box, and set start and goal. Put a goal inside a box: preflight blocks it and says why. It checks the standing footprint and the map bounds; route feasibility is left to a rehearsal. Save the arena.
3. **Rehearse:** choose WX-RF (preselected at its own K8/ODE6 budget), your arena and a preset. Set *Planner latency* 200 ms, *Anchor* predict (latency-aware), and *Actuator limits* "Current G1 · 139/139/88 (training)". Run.
   - The view attaches live (LIVE badge, follow camera).
   - Intent → *Planner selection* reads "Executing for …", with the request time and the time the plan started driving SONIC 200 ms later.
   - Health → *Timing vs budget* explains that simulated time does not wait for planner compute.
   - When the recording opens: Health → *Run outcome* → *Leg torque vs limit* marks leg joints AT LIMIT, with substep counts, and lists arm or waist joints separately.
4. **Runs:** filter by actuator profile. Read the report groups: goal rate with 95% Wilson intervals, post-hoc reach, torque at limit, predicted-anchor error.
   - Tick runs to overlay their paths.
   - Export the CSV.
5. **System:** check the pipeline map (planner → ZMQ → SONIC → DDS) and the robot node's hip limits. Then read the Unitree contract with its open, mitigated and resolved discrepancies.
6. **L3 (operator):** run the command in [REALTIME_REHEARSAL](REALTIME_REHEARSAL.md). Within 10 s, Studio lists the run under "Real-time rehearsals (L3)", with its actuator limits.

The narrated walkthrough of the same features is the video in `evidence/video-20261020/`.
