Unitree G1 · learned navigation · simulation first

Rehearse first. See what the robot sees. The operator says go.

G1 Deploy Studio is a browser cockpit for deploying a learned navigation policy on a humanoid. A learned planner plans from the robot's own LiDAR map, a tracking policy turns the plan into motor targets, and Studio shows every step: what the robot perceives, where it plans to go, and whether a goal passes Studio's checks before it is sent. Studio never commands a motor.

Goal checks

Staged. On the real robot Studio would now send this goal to node.py, read it back and show it as verified. Nothing moves until the operator presses g.

Each walk is a fresh session from the start mark: boot with a 1 s pre-scan, one goal, Go (node.py's own 0.5 s pre-scan), walk, stand, end. Your click snaps to the nearest recorded goal on a 0.4 m grid; each goal was recorded once, with one seed. The planner never sees the real boxes, only its map. What this is not.

How the pieces fit

On the robot day everything runs on the deploy PC next to the G1. Studio attaches there on loopback: it listens to the streams, and it may send node.py a checked goal or a request to stand, and ask for its status. Click a part to see what it does.

Studio may send

  • goal to node.py, only after the checks pass and only while the robot stands still
  • stand to node.py
  • status requests, to read the goal back

Studio never sends

  • go: the operator presses g on the console or F1 on the remote
  • quit, or anything to the SONIC runner
  • any DDS message: it has no DDS participant and no motor-command path

People keep

  • the wireless remote: D-up hands control to SONIC standing (not near overhead obstacles); Select is the runner's damping E-stop (the robot drops: gantry or spotter only)
  • the physical E-stop and a gantry or spotter
  • the decision to walk

Exposure today: Studio binds only loopback, but node.py (tcp://*:5562, which accepts go and quit, and *:5556) and the LIO bridge (*:5561) bind every interface. Until they bind 127.0.0.1 (proposal U3 to the deploy repository), firewall the robot network.

What rehearsing found

Running hours of simulated walks before a real one is the point. These came out of it; where there is an example, it is one of the recordings above.

What this is, and what it is not

  • The deploy stack's software: the frozen Flow student planner, the SONIC tracking policy and node.py's state machine, run on CPU in MuJoCo with a simulated MID-360 LiDAR
  • The robot's deploy settings: planner budget of 16 candidates and 10 ODE steps, a 160 ms planner latency with predictive anchoring, LIO-level odometry drift
  • Studio's own goal checks, computed on the map the robot had at the start mark
  • Every walk that was recorded, including the ones that went wrong, with contact and the true final distance shown
  • Not a run on a real robot: nothing here has run on hardware
  • Not live: walks were recorded in advance, one per goal, one seed; your browser plays them back and runs no policy
  • Not the C++ runner and DDS chain: the simulated robot is an in-process lockstep loop
  • Not continuous: goals snap to a 0.4 m grid and every walk starts from the start mark

    Use it

    Studio is a Python gateway and a browser app. It runs on loopback next to the deployment it watches. The page above is a demo of one workspace; this is the tool.

    Run it

    git clone https://github.com/linjiw/g1-deploy-studio
cd g1-deploy-studio
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
npm ci
.venv/bin/python -m studio.server --port 8790
# then open http://127.0.0.1:8790/

    What you get from this repository alone: Replay of your own recordings, and the tests. Rehearsals, Navigate's simulated robot and the robot link read the deploy stack (g1-student-deploy with the Flow student bundle and the SONIC policy), which is not public. No recordings, weights or robot meshes ship with the code.
